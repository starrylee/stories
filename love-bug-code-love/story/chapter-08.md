# 第八章 第一次救火

磐石风险期第五个月，出了个不大不小的故障。

故障是从周二开始出现的，很轻，轻得没人拿它当回事。

磐石的联调环境里，客户工单的批量推送任务偶发超时。一天三到五次，每次只挂一两个任务，五秒后自动重试，重试全部成功。P3 级别，连告警群都只是懒洋洋地弹一条黄色消息：**推送任务 21874 执行超时，已自动重试成功。**

真正让人不舒服的是第五天。

到周五中午，超时累计四十一次，仍然全部重试成功，仍然无规律——早上九点有，下午三点有，凌晨两点也有；大任务超，小任务也超；同一个通道昨天超今天就不超。老张盯着告警曲线看了一下午，最后在值班群里留下一句话：

"这玩意儿要么自己好，要么等它变大。现在的信息量，够不着。"

没人反对。这就是偶发故障的宿命：数据不够，规律不显，监控全绿，日志干净。应用没有重启过，依赖服务没有抖动过，数据库慢查询为零，网络重传为零。一个健康的系统，在随机时刻随机地超时——像一个人体检全正常，但每天随机心悸两次。

周六上午，因为磐石的联调要复用推送通道做一轮全链路演练，老宋把沈见微也拉进了排查群："多双眼睛。你就当打杂，端茶倒水递日志。"

战时还没到开战情室的程度，就是研发区拉了个临时排查群，十几个人，两块屏幕，一白板写满了划掉的假设。

"连接池？"有人问。

"看了，池子水位常年百分之三十，峰值都没满过。"

"线程池？"

"队列深度为零。"

"下游限流？"

"下游说他们什么都没干。"

白板上的假设一条一条增加，又被一条一条划掉。到中午，划掉的红线比假设本身还多。

沈见微坐在最角落，干着她被拉来干的活：递日志。有人要看哪个时间段的应用日志，她就按时间戳切出来发过去。三个小时，她切了四十多份日志。

递日志这个活儿有个别人不太在意的好处：每一份日志都是同一个系统在同一批超时事件周围的切片，切多了，切片之间会互相说话。

到下午一点四十分，她发现了一件很小的事。

她把它写在了自己的草稿纸上，没敢直接说——一件这么小的事，在一个十几个人排查了三个半小时的群里，说出来是需要点脸皮的。她先自己验了一遍：四十一次超时，她把每一次的时间戳单独摘出来，贴到联调流量的曲线上。

四十一个点，全部落在曲线的谷底。

不是随机。超时从不发生在高峰，全部发生在低峰——任务队列越闲的时刻，越超。

她盯着这四十一个点看了两分钟，忽然意识到自己可能碰到了那个"够不着"的信息量。忙的时候不超、闲的时候超，这个规律反直觉到没有一条已有假设能解释它——所以大家找规律的时候，都本能地在"忙"里找。

她举手的时候手心有点出汗。

"我说个现象。"她说，"四十一次超时，全部发生在流量低谷。"

群里安静了一秒。有人立刻把她的点贴上大屏。

四十个红点撒在流量曲线上，像一串脚印，全部踩在谷底，一个山头都没翻过。

"……为什么闲的时候超？"有人喃喃。

"因为闲，"沈见微已经在翻她那沓日志切片了，"所以池子里的连接一直没被用。"

这句话说完，排查方向在三十秒内完成了集体转向：连接在空闲状态下发生了什么。

空闲连接、超时、任务来了却拿不到可用连接——三个词拼在一起指向一个所有人第一轮就查过、因而第二轮不太好意思再查的地方：连接池的配置。当时查的是池子水位和最大连接数，都对。现在要查的是另一组参数：空闲回收时间、保活间隔、最小存活。

"推送通道的连接池配置，最近有人动过吗？"

没人动过。配置平台的变更记录干干净净——上一个变更在三个月前。

配置没变。那什么变了？

"配置没变的话，"沈见微慢慢地说，"让配置生效的东西，变了。"

代码。

---

三点二十，她坐在自己的工位上，面前摊着推送通道服务最近一个月的合入记录。三十七个提交。

老宋端着泡面凑过来："你怎么看这个？三十多个 diff，一个一个看要看到明天。"

"不用全看。"她滚动着列表，"看发布日期。故障第一次出现是周二。上一次发布是上周三。中间隔了六天——如果超时是这次发布带进来的，前六天是它攒概率的时间。"

她把上周三那次发布包含的提交单独滤出来：五个。

第一个，业务需求，改动在工单文案组装模块，无关。第二个，依赖升级，锁文件三百多行，无关。第三个，第四个，都是小改动。

第五个，提交说明写着：**"调整连接池空闲回收策略"**。

她点开 diff。改动很小，两行：

```
- idleTimeout: 600000
+ idleTimeout: 30000
```

注释，一行小字，趴在两行改动的下面：

```
// 临时：联调环境连接数不够，把空闲回收调小先顶着，演练后改回
```

演练后改回。

她翻这个提交之后的所有记录。没有"改回"。六天了，"临时"两个字还活着，活在联调环境的每一个连接池里。

"十分钟回收变成三十秒回收，"她说，"低峰期任务间隔经常超过三十秒——池子里的连接一闲下来就被回收。下一批任务到的时候，池子在建新连接，建连接要握手、要鉴权，冷启动一两秒，超过五秒的任务等待阈值就是超时。高峰期任务一个接一个，连接永远'不闲'，永远不会被回收——所以忙的时候从来不超。"

她在白板上画了条时间线：任务与任务之间那道超过三十秒的空隙，像退潮后的滩涂——连接是搁浅的鱼，三十秒内没有被下一个浪头救走的，就被回收了。

"重试为什么都成功？"

"因为重试的时候，池子已经把新连接建好了。"她说，"所以这个故障永远'自愈'，也永远不改。它只有在你闲的时候咬你一口，忙起来它就装死。"

白板前安静了几秒。有人一拍脑门："我说呢！我盯着告警想找规律，全盯着高峰那几个毛刺看——"

"高峰的毛刺是正常的毛刺，"沈见微说，"这种故障的脾气是反的。它不咬忙人，专咬闲人。"

有人已经开始在群里发结论，发修复方案：idleTimeout 改回十分钟，当晚发布窗口就走紧急通道。

按理说，到这就结束了。定位、修复、验证、复盘，一条流水线。

但沈见微多做了一件事。

她盯着那条注释，"临时：联调环境连接数不够"，多看了一会儿。测试环境的问题，改在代码里，用一行注释标记"演练后改回"——这个做法本身，就是事故。于是她顺手点开了这个提交的评审记录，想看看 review 的人当时说了什么。

评审记录只有一行：

**批准合入：陈曦（上周三 21:47）**

提交时间：上周三 21:45 48 秒。

提交到批准，间隔九十秒。

一个改动连接池核心参数的提交，两行代码加一行"演练后改回"的注释，在九十秒内走完了 review。她想起自己那个改了个函数命名的提交，江叙白看了一整晚——当然，那个评审记录里也有一行字，"用词就是接口"。

她没多想，把评审记录的截图存进了"工作留痕"。职业习惯，先存档，不判断。

存的时候她多看了一眼那个名字。陈曦，磐石联调组的值班评审——一个和她同期入职的年轻人，忙碌、老实、总是来不及。她想起九十秒这个数字在哪家公司都长得差不多，想起自己的名字有朝一日也可能挂在某个九十秒上，指尖顿了一下。

先存档，不判断。她合上了文件夹。

---

当晚十点，修复上线。此后四十八小时，超时为零。

复盘会定在下周一。临时排查群解散前，联调组的接口人在群里发了长长一段感谢，最后@她："沈工那个'低谷聚类'的分析思路，能不能整理成文档？我想放进磐石的故障手册。这毛病联调环境里出过三次类似的，每次都是不了了之。"

她回了个"好"。

十一点，她整理完文档初稿，检查最后一遍的时候，发现群里有条新消息。是江叙白——他从头到尾没在排查群里说过话，此刻也只发了一行：

**"低谷聚类。这个词可以。"**

没有夸人。夸的是词。

沈见微看着那五个字，莫名其妙地笑了一下，又赶紧收住。她回了个"收到"，关掉电脑。

走出研发楼的时候她想，这篇文档的标题就叫《低峰期偶发超时的空闲连接回收竞态分析》好了——太长，缩一下：**《闲出来的超时》**。

嗯，还是正经点。毕竟是故障手册。

---

她不知道的是——她顺手点开的那个九十秒，会在不远的将来，把一个名字从她的记忆深处钓上来。

不是陈曦的名字。

是另一个人的。

那个此刻正坐在另一栋楼里、和磐石毫无交集、但即将在项目交接之后接管这一切的人——她还不知道，这个人有一种把"临时的改动"变成"永久的习惯"的天赋，而这个天赋的第一处笔迹，已经通过一个九十秒的值班评审，第一次爬进了她的视野边缘。

守护她的人在看尾部。而她不知道的是，她也已经在无意之中，看到了另一个人将来会留下的东西的形状。

一个用"临时"命名、永远不会"改回"的形状。

先存档，不判断。档案在长。
